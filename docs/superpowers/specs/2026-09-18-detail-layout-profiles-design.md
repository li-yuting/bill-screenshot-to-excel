# 工具二：单笔交易详情页支持多种版式（版式档案）

- 日期：2026-09-18
- 状态：已实现
- 影响文件：`billtools/detail.py`（主要）、`billtools/excel.py`、`billtools/app.py`

## 一、问题

新到一批截图（`账单5/`，14 张 1061×2300 单屏图）是**建行 App 的「明细详情」单笔详情页**。
跑工具二时 **14 张全被跳过、0 笔**，最后抛 `ValueError: 没有解析出任何交易`。

先分清责任：**OCR 没问题**（每张读出 27~30 个文字块，字段值都认得挺准），
是解析规则认不出这套版式。两个精确原因：

### 根因 1：金额正则匹配不了「￥-129.00」

建行的支出金额写作 **币符在前、负号在后**，而老正则把负号写死在开头：

```
MONEY_RE = (-?)\s*[￥¥]?\s*([\d,]+)\.(\d{2})
MONEY_RE.fullmatch('-69.00')   -> -69.0   ← 老版式能过
MONEY_RE.fullmatch('￥-129.00') -> None     ← 建行版式挂了（[\d,] 不含负号）
```

`_top_amount()` 因此返回 `None`，`parse_page` 抛「没识别到金额」，全数跳过。

### 根因 2：标签表是写死的七个

| | 标签 |
|---|---|
| 老版式（收支详情单页） | 交易卡号 / 交易账户 / 交易户名 / 交易时间 / 业务摘要 / 交易场所 / 交易金额 |
| 建行「明细详情」 | 交易账户 / 交易时间 / **支付机构 / 商户名称 / 商品信息 / 交易方式 / 对方账户 / 记账日 / 账户余额 / 交易流水号** |

只有「交易账户」「交易时间」对得上。

### 顺带查出的一个「侥幸过关」

`TOP_ZONE = 550` 也是**绝对像素**（顶部金额区写死为 `y < 550`）。
建行那批图的大金额在 **y = 543.7**，距离出界只差 **6.3 像素** —— 这次是侥幸过的，
换个机型/系统字号立刻又废。和 `statement.py` 上一轮修的问题同源。

## 二、设计：版式档案（Profile）

把「认哪些标签、标签映射到哪个字段」抽成可声明的档案，取值逻辑共用一份。

```python
@dataclass(frozen=True)
class Profile:
    key: str
    title: str
    labels: tuple[str, ...]        # 本版式的全部标签
    fields: dict[str, str]         # 标签 -> Detail 属性名；空串表示不进核心字段
    summary_label: str | None      # 摘要取自哪个标签
    balance_label: str | None      # 余额取自哪个标签的值
    booking_label: str | None      # 记账日取自哪个标签
```

**版式识别**：按「命中的特征标签数」自动挑，取命中最多的那个。实测老版式命中 7、建行命中 10，
判据很干净；命中数相同时取档案表里靠前的，不需要用户选。

**字段映射**：

| 建行标签 | 映射到 |
|---|---|
| 交易账户 / 交易时间 | `account` / `time`（与老版式同名字段） |
| 支付机构 + 商户名称 | 拼成 `place`（`支付机构 / 商户名`），与老版式的「宝付-好分期」同构，使「按交易场所」汇总对两种版式都成立 |
| 账户余额 | `balance` |
| 记账日 | `booking`（用于日期交叉校验） |
| 商品信息 / 交易方式 / 对方账户 / 交易流水号 | `extra`，导出时动态加列 |
| （无标签）摘要 | 顶部大金额**上方**最近的短文本块（建行把「消费/充值」放在金额上方） |

### 2.1 去掉 `TOP_ZONE`，改自校准

- **字段区上沿** = 最靠上的**标签块**的 y（不再写死 550）
- **值区下沿** = 标签 y + `VALUE_ZONE_RATIO(0.8)` × 相邻标签间距的**中位数**

### 2.2 换行的长值要拼起来

交易流水号会被 OCR 断成两块：头一段在标签**上方**、尾一段在标签**下方**，
两段间隔 32px，超过「同一行」的容差（30px）。

老逻辑「取行内最右一块」实测**丢掉了流水号最后一位**。
改成：值区内的块按 `(y, x)` 排序后**拼起来**。
同一个规则顺带救回了「对方账户」的两行（商户名 + 卡号）。

### 2.3 其余修复

| 问题 | 修法 |
|---|---|
| `￥-129.00`（负号在币符后） | 正则改为 `([￥¥]?)\s*(-?)\s*([\d,]+)\.(\d{2})`，两种写法都认 |
| 余额带币符和空格（`￥ 79.78`） | 统一走 `_found_any()` 搜数并转 float |
| 商户名粘上客服电话（`某商户电话400…`） | 剥尾部的 `电话?\d{6,}` |
| 建行版式没有「交易金额」，少了一个校验点 | 用 **「记账日」是否等于「交易时间」的日期**补上（新字段 `booking` + `date_consistent`），并在自动校验里如实说明哪个检查被跳过 |

## 三、实测

| 输入 | 结果 |
|---|---|
| `账单5/`（建行明细详情，14 张） | **14 笔全中**，关键字段零缺失 |
| `账单2/`（收支详情单页，43 张唯一） | 与旧基线一致（回归，见下） |

顺带修好的字段质量：交易流水号尾位不再丢、对方账户两行拼接、商户名不再粘电话号。

## 五、风险

| 风险 | 缓解 |
|---|---|
| 版式自动识别挑错档案 | 按「命中标签数」取最多；命中 0 个时会明确报错、不静默产出空字段 |
| 值区下沿算错，把下一行的值吸进来 | 用相邻标签间距中位数（不写死）；实测两栏值不会串行 |
| 拼接把不该拼的拼起来 | 只拼「标签行带内、且在标签右侧、且本身不是标签」的块；老版式每个字段都是单块，回归已验证 |
| 新增的动态列让表结构不稳定 | 只加「至少有一条非空值」的列，且顺序按标签在档案里的声明顺序，同一批数据结果稳定 |

## 六、不做的事

- **不做「不预设标签」的完全通用抽取**：列数会随图变、跨图可能不齐，
  汇总维度（按摘要 / 按交易场所）会失去语义。加一种版式的成本已经降到「往档案表里加一条」，
  不值得为通用性牺牲输出的确定性。
- **不改动 `statement.py` 的列表版式逻辑**：两者输入形态不同，共用取值机制但没有共用入口。
